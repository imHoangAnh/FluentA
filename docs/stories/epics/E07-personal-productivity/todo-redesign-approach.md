# E07 Todo Redesign Approach

## Recommended Path

Deliver the approved D1-D58 behavior as four dependency-ordered high-risk
vertical stories. Each story must include its visible UI, owner-scoped API,
domain/persistence changes, automated proof, and relevant product-contract
update. Do not create a backend-only or frontend-only intermediate story.

1. `US-TODO-003` replaces the current Day surface with the My Day core:
   today-only quick creation, compact rows, selection and side-by-side details,
   durable importance, title/note autosave, confirmed deletion, the restricted
   context menu, local automatic-sort preference, and durable manual reorder.
2. `US-TODO-004` adds the exact repeat enum and the atomic occurrence lifecycle,
   including next-occurrence generation and safe reopening behavior.
3. `US-TODO-005` adds one durable reminder per task, the API-hosted minute
   scanner, idempotent in-app notification delivery, and owned task deep-link
   selection from notifications.
4. `US-TODO-006` delivers the approved Week v2 board, per-day quick creation,
   the shared details panel, icon-only importance, server-owned duplication,
   preserved navigation/reorder/cross-day movement, and final responsive and
   release proof.

This order keeps every intermediate state demonstrable. It also prevents Week
duplication from reconstructing reminder and recurrence data before those
contracts exist.

## Proposed Persistence And Domain Shape

Extend `todo_items` incrementally rather than introducing a second Todo table.

| Story | Proposed durable fields | Cause and effect |
| --- | --- | --- |
| `US-TODO-003` | `is_important` | The row star and detail-panel star read and write one owner-scoped value. |
| `US-TODO-004` | nullable `repeat_pattern`, nullable `generated_from_todo_id`, `is_generated_occurrence_pristine` | A completed occurrence can create exactly one traceable next occurrence, and reopening can distinguish an unchanged generated child from one the user edited. |
| `US-TODO-005` | nullable `reminder_time`, `reminder_time_zone_id`, `reminder_scheduled_at_utc`, and `reminder_sent_at_utc` | The UI retains the chosen wall-clock time while delivery uses a fixed UTC instant that does not move after a device timezone change. |

`repeat_pattern` accepts only `Daily`, `Weekdays`, `Weekly`, `Monthly`, and
`Yearly`. A unique nullable index on `generated_from_todo_id` prevents two next
occurrences from being created for one completed source occurrence. Any
user-authored mutation of an autogenerated child makes it non-pristine. A
completion/reopen operation and its generated-child mutation must commit in one
database transaction.

The reminder save request should carry the selected `HH:mm`, the browser IANA
timezone id, and the browser-resolved UTC instant. The API must convert that
instant back through the supplied timezone and prove that it maps to the task
date and selected time before accepting it. Therefore an arbitrary or invalid
instant is rejected, while an ambiguous daylight-saving time preserves the
exact instant the browser selected. This contract must be proven on both the
Windows development runtime and the Linux-targeted runtime during validation.

## Proposed API Shape

Preserve the existing `/api/v1/todos` list, create, field-scoped patch, and
delete routes. Add fields to the existing Todo projection only as their owning
story lands.

- Add `isImportant` to create/update/read contracts in `US-TODO-003`.
- Add `repeatPattern` and recurrence mutation metadata in `US-TODO-004`.
- Add reminder fields in `US-TODO-005`.
- Add owner-scoped `GET /api/v1/todos/{id}` in `US-TODO-005` so a notification
  can select a task even when it is not in today's list.
- Add `POST /api/v1/todos/{id}/duplicate` in `US-TODO-006`. The server reads the
  owned source, copies title, note, importance, reminder, and repeat, assigns a
  new identity on the same date, and always creates an incomplete task.

Mutation responses may add one nullable machine-readable `warningCode` without
replacing the existing Todo object shape. The two approved warnings are:

- `reminder-cleared-after-date-change` when a successful move makes the saved
  reminder past and the API clears it.
- `recurrence-next-retained` when reopening succeeds but an edited generated
  next occurrence is kept.

The frontend maps these codes to user-facing messages. It must not infer either
case by comparing cached objects.

## Reminder And Notification Delivery

The current source registers Hangfire recurring jobs inside
`FluentA.API`; there is no buildable `FluentA.Worker` project in the current
tree. `US-TODO-005` must follow that deployed source reality and register one
stable `todo-reminders` minute scanner through the existing recurring-job
registration seam.

The scanner queries incomplete, non-deleted tasks whose
`reminder_scheduled_at_utc` is due and whose `reminder_sent_at_utc` is null. In
one save it adds a Notification with a deterministic per-task/per-instant
deduplication key and marks the reminder sent. Retry proof must show that a
second scan creates no second notification.

Add an optional validated same-origin relative `actionPath` to notifications.
Todo reminder notifications use `/todo?taskId={ownedTaskId}`. Notification UI
marks the item read and navigates only when this server-provided relative path
passes validation. `/todo` then uses the authenticated by-id Todo read and opens
the shared detail panel. Missing, deleted, or foreign tasks produce a safe
not-found message without revealing ownership.

## Frontend Ownership And Layout

- Keep route orchestration in `TodoPage.tsx`, but extract focused My Day list,
  Week board, task row, context menu, and detail-panel components rather than
  growing one page container further.
- Keep server state in the existing Todo query/API seam. Store only the active
  automatic sort choice in browser local storage.
- Automatic sorting is derived independently inside incomplete and completed
  groups. Starting an incomplete-task drag clears the local automatic sort and
  persists the resulting manual `sortOrder`. Completed tasks never enter the
  drag surface and remain newest-completed first.
- Keep task rows compact: title plus completion and icon-only star. Notes,
  reminder, repeat, and date remain detail-only.
- Keep the details panel beside the content. In Week desktop layout, use an
  approximately 4:1 board/panel split. At narrower supported widths, allow
  local board scrolling while preventing page-level horizontal overflow.
- Move Week's accessible explicit Move command into the keyboard-reachable
  context menu so the row still satisfies the approved three-control visual
  contract. Right-click and Shift+F10 open the same menu.

## Rejected Alternatives

1. **Implement all D1-D58 in one story.** Rejected because a recurrence defect,
   reminder retry defect, or Week regression would share one proof gate and be
   difficult to isolate.
2. **Split by technical layer.** Rejected because a schema/API-only story is not
   a user-demonstrable Todo outcome and would leave unsupported UI states.
3. **Create one Hangfire job per reminder.** Rejected because edits,
   completion, movement, and deletion would require fragile external job
   synchronization. One scanner keeps PostgreSQL as source of truth.
4. **Create recurring children in the browser.** Rejected because retries and
   concurrent clients can create duplicates and bypass an atomic lineage rule.
5. **Detect edited generated occurrences with timestamps or field comparison.**
   Rejected because reorder/date changes and later copied fields make that test
   ambiguous. Explicit pristine state records user mutation intent.
6. **Duplicate by posting the visible Week row back to create.** Rejected
   because the compact row intentionally omits note, reminder, and repeat.
7. **Put an action callback or arbitrary external URL in a Notification.**
   Rejected because persisted executable behavior or external navigation would
   cross a trust boundary. Only a validated relative application path is used.

## Risks And Required Proof

| Risk | Cause and effect | Required proof |
| --- | --- | --- |
| Existing Todo regression | My Day replaces a shipped Day UI and Week later changes its presentation | focused Vitest and Chromium coverage for create/select/edit/complete/delete/sort/reorder plus existing Todo E2E regression |
| Recurrence duplication | two completion requests can each attempt to create a child | unique lineage constraint plus application and live PostgreSQL concurrency/retry proof |
| Incorrect recurrence dates | weekdays, month ends, and leap years have non-linear transitions | domain table tests for weekends, 28/29/30/31-day months, and leap/non-leap years |
| Wrong reminder instant | browser timezone, DST ambiguity, and server timezone support can disagree | round-trip contract tests and Windows/Linux validation for normal, invalid, and ambiguous local times |
| Duplicate notifications | scanner retry can add the same reminder twice | deterministic dedupe key, same-save marker, application test, and live two-run job proof |
| Ownership leak | by-id selection, duplicate, or notification navigation can expose a foreign task | authenticated integration tests returning not found for foreign/deleted ids |
| Lost reminder on move/complete | date and completion mutations alter delivery eligibility | application tests for clear-and-warn, cancel, recurrence copy, and no later notification |
| Layout overflow | seven columns plus details can compress or overflow the page | screenshots and DOM overflow assertions at approved desktop widths plus narrow local-scroll proof |
| Dirty worktree damage | Todo/product files already contain unrelated user edits | path-scoped patches, diff review before every story, and final `git status`/`git diff --check` |
| Runtime documentation drift | old Worker documentation/matrix evidence conflicts with the current source tree | validation records the executable host from source and release docs reconcile the stale runtime wording without inventing a Worker project |

## Expected Integration Boundaries

Backend:

- `FluentA.Domain/Todos` for importance, recurrence rules, reminder state, and
  generated-occurrence lifecycle.
- `FluentA.Application/Todos` for owner-scoped commands/queries, mutation
  warnings, atomic recurrence behavior, and focused tests.
- `FluentA.Infrastructure/Persistence` for mappings, repository transaction
  behavior, migrations, indexes, and snapshot updates.
- `FluentA.API/Controllers/TodosController.cs` for additive Todo routes and
  `FluentA.API/Jobs` for the one reminder scanner registration.
- Notification entity/projection/UI only where required for the optional safe
  action path.

Frontend:

- `src/frontend/src/features/todo` for API types, query state, My Day, Week,
  details, menus, and focused tests.
- `src/frontend/src/features/notifications` for read-and-navigate behavior.
- Todo and notification Playwright specs for authenticated end-to-end proof.

Tracked contracts:

- Update `docs/product/personal-productivity.md` surgically in each story while
  preserving unrelated Habit/Countdown edits.
- Add decision `0053-todo-recurrence-reminder-and-notification-navigation.md`
  after validation confirms transaction, timezone, scanner, and relative-path
  choices.
- Refresh the current story packet and Harness proof after every story; do not
  mark a row implemented from build output alone.

## Planning Exit State

- The approved D1-D58 context is linked from four registered high-risk stories.
- `US-TODO-003` has an executable packet small enough to validate now.
- Later stories have explicit dependencies and observable exit states but do
  not authorize implementation ahead of their own validation.
- The human reviews this plan before `harness-validating` begins.
